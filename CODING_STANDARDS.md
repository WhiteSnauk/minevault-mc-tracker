# Стандарты кодирования проекта MineVault (CODING_STANDARDS.md)

Настоящий документ устанавливает единые правила оформления исходного кода, именования сущностей, обработки ошибок и работы с системой контроля версий Git в рамках разработки веб-приложения **MineVault** (стек: JavaScript ES6+ / Node.js / HTML5 / CSS3).

## 1. Правила именования
| Элемент кода | Стиль записи | Пример в проекте |
| :--- | :--- | :--- |
| **Классы и модели** | `PascalCase` | `WorldServer`, `CoordinatePoint`, `AuthService` |
| **Функции и методы** | `camelCase` (глагол + существительное) | `createWorld()`, `convertNetherRatio()`, `registerUser()` |
| **Переменные и параметры** | `camelCase` | `worldTitle`, `netherCoords`, `passwordHash` |
| **Глобальные константы** | `UPPER_SNAKE_CASE` | `NETHER_RATIO`, `MIN_PASSWORD_LENGTH`, `SUPPORTED_DIMENSIONS` |
| **Файлы модулей и классов** | `PascalCase.js` / `camelCase.js` | `AuthModule.js`, `WorldModule.js`, `CoordinateModule.js` |
| **Каталоги** | `kebab-case` или строчный `lowercase` | `src/modules/authentication/`, `src/services/` |

## 2. Форматирование кода
* **Отступы:** строго 2 пробела (использование символов табуляции запрещено).
* **Кавычки:** двойные кавычки `"` для строковых литералов или обратные кавычки `` ` `` для шаблонной интерполяции.
* **Точка с запятой:** обязательна в конце каждой инструкции (`;`).
* **Максимальная длина строки:** не более 100 символов для сохранения читаемости на любом экране.
* **Фигурные скобки:** стиль K&R (открывающая скобка `{` на той же строке, что и объявление функции/условия).

## 3. Организация файлов и архитектура
* Соблюдается принцип единственной ответственности (**SRP**): один файл отвечает за одну модель, сервис или программный модуль.
* Запрещено смешивать логику пользовательского интерфейса (UI), бизнес-логику и работу с хранилищем данных в одном файле.
* Все импорты располагаются строго в верхней части файла.

## 4. Требования к комментариям
* Перед каждым классом и публичным методом оформляется блок **JSDoc** (`/** ... */`) с описанием назначения, параметров `@param` и возвращаемого значения `@returns`.
* Однострочные комментарии `//` используются только для пояснения неочевидной бизнес-логики (например, округления координат при делении на 8), а не для дублирования очевидного кода.

## 5. Обработка ошибок и валидация
* Все входные данные пользовательских форм и API проверяются до выполнения бизнес-операций.
* При нарушении бизнес-правил или некорректных типах данных выбрасываются информативные исключения `Error` с понятным сообщением на русском языке.
* Вызовы критических операций оборачиваются в блоки `try { ... } catch (error) { ... }`.

## 6. Требования к безопасности
* Запрещено хранить и логировать пароли пользователей в открытом виде — используется криптографическое хеширование (`crypto.scryptSync` / `sha256` с солью).
* Доступ к изменению или удалению карточки мира/координат разрешается только после проверки совпадения `ownerId` с идентификатором текущего пользователя.
* Секретные ключи и локальные настройки среды исключаются из репозитория через `.gitignore`.

## 7. Правила работы с Git
* Каждый логически завершённый этап фиксируется отдельным коммитом.
* Сообщения коммитов оформляются по соглашению **Conventional Commits**:
  * `feat:` — добавление нового функционального модуля;
  * `fix:` — исправление ошибки;
  * `docs:` — обновление документации (`README.md`, `CODING_STANDARDS.md`);
  * `test:` — добавление или обновление тестов.
